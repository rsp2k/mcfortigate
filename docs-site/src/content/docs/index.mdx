## Why not just wrap the REST API

The obvious way to build this is one tool per FortiOS endpoint returning raw
JSON, and that turns out to work badly. A single FortiOS policy object carries
more than eighty fields, most of them empty strings, unused IPv6 arrays, and
internal UUIDs. Ask a model *which policies allow traffic into the DMZ* against
a raw wrapper and it spends most of its attention on `"srcaddr6": []` before it
finds anything useful.

So the tools here are shaped around the questions rather than around the
endpoints. `find_references` answers whether an object is safe to delete by
asking the appliance's own reference lookup — the one the web UI uses, which
knows all 234 tables that can reference an interface rather than the five a
hand-rolled scan would check. `find_device` merges the wireless client list,
the DHCP lease table, and the ARP table into a single record per device, which
requires canonicalizing the MAC first, on both case and punctuation, or one
device indexes as two and reports as unknown. That work happens once, here,
instead of being rediscovered by every model that asks.

[The long version of the argument](/explanation/question-shaped-tools/) is worth
reading before you decide how much of your own tooling to shape this way.

## Install

<Code
  lang="bash"
  title="Terminal"
  code={`printf 'FortiGate API token: '; read -rs FORTIGATE_TOKEN; echo

claude mcp add fortigate \\
  --env FORTIGATE_HOST=fgt.example.com \\
  --env FORTIGATE_TOKEN="$FORTIGATE_TOKEN" \\
  -- uvx mcfortigate`}
/>

That is the whole setup, once you have a read-only REST API admin on the
appliance. [Getting started](/tutorials/getting-started/) walks through creating
one.

The token goes through a variable rather than onto the command line, so shell
history records `"$FORTIGATE_TOKEN"` instead of the credential itself.

  <Card title="Read-only, structurally" icon="approve-check">
    Every tool issues `GET` and nothing else, and says so through the MCP
    `readOnlyHint` annotation. There is no create, update, or delete path in the
    codebase to disable, misconfigure, or talk a model into reaching.
    [How that is enforced](/explanation/read-only/).
  </Card>
  <Card title="Configuration and live state are different" icon="random">
    A DHCP-assigned default route is in the live routing table and will never be
    in the static route configuration. The tools keep the two apart on purpose.
    [Why it matters](/explanation/config-vs-live/).
  </Card>
  <Card title="FortiOS quirks, already handled" icon="warning">
    Booleans are the strings `"enable"` and `"disable"`, so `bool()` reads every
    disabled thing as enabled. That one mistake once flipped every route to
    blackhole. [The full catalogue](/explanation/fortios-quirks/).
  </Card>
  <Card title="Several appliances, short aliases" icon="setting">
    Set `FORTIGATE_TARGETS` and the keys become the `target` argument on every
    tool. Omit it when only one is configured.

  </Card>
